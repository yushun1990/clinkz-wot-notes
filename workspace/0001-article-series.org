#+title: 0001 Articles Series

建议把知乎内容分成四个系列

不要把全部文章都叫“ClinkZ-WoT 开发日志”。

建议建立四条相互关联、但读者群不同的内容线。

* 系列一：重新理解 WoT

这是入门和传播系列，面向普通物联网开发者。

** 01.为什么物联网平台不应该从 MQTT Topic 开始设计

核心问题：

- 传统 IoT 系统为什么容易被协议绑死；
- Topic、URL、设备指令为什么不是业务语义；
- TD、Property、Action、Event 能提供什么；
- “Thing 语义”和“协议通信”的区别。

这是最适合作为第一篇的文章。

** 02. W3C WoT 到底解决什么问题？它不是另一种物联网协议

重点解释：

- WoT 不是 MQTT 的竞争者；
- TD 不负责传输；
- WoT 如何统一 HTTP、MQTT、Zenoh 等协议之上的交互模型；
- 为什么 WoT 更像浏览器世界中的 Web API 描述与运行模型。

** 03. Thing Description 不是设备配置文件，而是语义契约

可以从一个温度传感器 TD 展开：

- Property、Action、Event；
- DataSchema；
- Form；
- security；
- extension members；
- 为什么 TD 中不能塞运行时连接、缓存和执行状态。

** 04. 一个 Thing 同时提供 HTTP、HTTPS 和 Zenoh，客户端该选哪个？

这篇来自你之前一直关心的 form selection。

可以讨论：

- 为什么不能简单“选第一个 form”；
- operation 是否匹配；
- security 是否可用；
- Binding 是否已注册；
- -协议能力和策略；
- fallback 和 retry 的区别；
- 为什么选择结果必须进入 Plan。

** 05.《ConsumedThing 和 ProducedThing：WoT 的客户端与服务端模型》

围绕两种方向解释：

#+BEGIN_SRC yaml
ConsumedThing：应用消费远程 Thing
ProducedThing：应用向外提供 Thing
#+END_SRC

重点写二者为什么共享语义，但生命周期并不对称。

** 06.《WoT Directory 是什么？为什么 ClinkZ-WoT 不实现 Directory 服务》

说明：

- Discovery client 与 Directory server 的区别；
- 为什么引擎只定义客户端边界；
- 存储、索引、查询、权限和多租户为什么属于平台，而不是 runtime core。

* 系列二：ClinkZ-WoT 架构设计

这是你的核心技术品牌系列。

** 07.《从 TD 到一次属性读取：ClinkZ-WoT 的完整执行链》

建议以 property read 为例：

#+BEGIN_SRC yaml
TD

 -> Logical Plan
 -> Binding Artifact
 -> Plan Set
 -> OutboundRequest
 -> Binding
 -> Response Validation

 #+END_SRC

它可以成为整个系列的总纲。

** 08. 为什么 WoT 运行时需要“编译计划”，而不是每次解释 TD

重点：

- TD 是高层描述；
- 热路径解释的成本；
- 默认值、base URL、security、form selection；
- 编译期错误和运行期错误；
- immutable plan 的可测试性；
- 为什么这不是 Cargo 编译。

** 09. Logical Plan 与 Binding Artifact：协议中立究竟如何实现

这是非常有技术辨识度的一篇。

解释：

- Logical Plan:
  读取 temperature，使用这个 form、这个 security 分支
- Zenoh Artifact:
  使用这个 key expression 和编码设置
- HTTP Artifact:
  使用 GET、这个 URL 模板和 Header 规则

说明哪些知识可以共享，哪些必须留在 Binding 内。

** 10. Servient 为什么必须成为 WoT 运行时的唯一编排者

重点写你曾经困惑并逐步确认的问题：

- Binding 能不能直接调用 Handler；
- 谁拥有 application registry；
- 谁做 security、schema 和 codec；
- 谁拥有 cancellation；
- 谁调度多个 Binding；
- 为什么不能把 Dispatch handle 交给 Binding。

** 11. Protocol Binding 只是协议适配器吗？一个完整 Binding 应该拥有什么

内容包括：

- capability；
- compiler extension；
- client execution；
- server route；
- subscription driver；
- emission；
- correlation；
- cleanup；
- resource footprint；
- complete registration bundle。

** 12. 为什么 ClinkZ-WoT V1 放弃动态插件，选择 Cargo 静态链接

这篇会很有现实意义。

可以完整记录你的思路变化：

- 希望安装 .so 获得新协议能力；
- 发现 Rust ABI、async、trait object、卸载和资源所有权问题；
- 考虑 WASM；
- 最终选择 Cargo-linked Binding；
- 通过重新编译、灰度发布获得“平台级动态能力”。

不要只写结论，要把被否决的路线一起写出来。

** 13. build.rs 能不能实现 Rust 插件系统？为什么答案通常是否定的

由上篇自然延伸：

- Cargo 何时解析依赖；
- build script 何时执行；
- 为什么 build.rs 不能临时增加 crate dependency；
- 类型身份、feature、target、lockfile；
- 真正的平台管理器该怎样生成组合工程。

** 14. 静态链接不等于不能动态扩展：IoT 平台的重新编译与灰度发布

把 ClinkZ 平台未来设想写出来：

#+BEGIN_SRC yaml
用户安装 Binding

 -> 构建新 Servient image
 -> 验证
 -> 灰度部署
 -> drain 旧实例

#+END_SRC

这篇同时有架构和产品价值。

* 系列三：Rust 运行时机制

这条线可以帮助你获得 Rust 技术作者身份，而不只局限于 WoT。

** 22. 为什么异步回调必须在锁外执行

用 ClinkZ-WoT 的两阶段模型解释：

*** 锁内：
- 校验 generation
- 预留资源
- 复制不可变输入
- 领取 callback lease

*** 锁外：
- 调用 Handler / Binding / Codec

*** 再次锁内：
- 校验 lease 和 generation

*** 提交结果

这是很通用的 Rust 并发文章。

** 23. HandlerContext 应该包含什么，不应该包含什么

- cancellation；

** 24. Deadline 为什么不能只是一个 u64

可以结合当前已经完成的 logical-time 和 deadline cleanup 工作：

- tick 来源；

- wrap；
- non-wrapping extended logical ticks；
- deadline 与 wall clock 的区别；
- cleanup 时钟语义。

当前逻辑时间、deadline cleanup 和 HandlerContext 已经完成对应实现切片，因此可以写成“设计 + 已实现验证”，但 API 仍应标注处于架构闭合期。

** 25. no_std 不只是去掉标准库：如何保持运行时语义一致

** 26. Pull-based Subscription 为什么比回调更适合运行时边界

** 27. 为什么 Subscription 不应该 Clone

用几个反例：

- 两个 clone 谁控制 stop；

- 谁负责 cleanup；
- 为什么多个消费者应该申请多个 SubscriptionId；
- 应用 fan-out 为什么应在 runtime 外完成。

** 28. subscribe_all_events 为什么不能简单循环订阅所有 Event

** 29. WorkBudget：在无统一 Executor 的系统中如何描述公平性

** 30. Fallible Cleanup：为什么析构函数不能是唯一清理机制

** 系列四：人与 AI 共同开发大型 Rust 项目

这可能是你最有差异化的内容。

很多人能写 Rust，很多人能谈 AI 编程，但很少有人真实记录：

如何让 AI 长期维护一个复杂系统的架构连续性。

** 31. 我如何让 AI 主导一个 Rust 架构项目，而不是只生成代码

不要写成“AI 很厉害”，而要写责任划分：

- Owner 决定愿景、现实约束、不可接受方向；
- AI 负责技术架构、API、工作包、风险和证据；
- Owner 的问题是 evidence input；
- AI 必须调查并做出技术判断；
- AI 不应把技术选择重新甩给 Owner。

** 32. 聊天记录不是项目记忆：为什么 AI 项目必须把上下文写回仓库

** 38. 不是所有改动都需要同样的架构审查

介绍当前 Category A/B/C：

- A：局部、增量、风险较低；
- B：跨模块契约；
- C：架构或 invariant 变化；
- 风险与审查深度对应；
- 避免小改动被重流程拖死，也避免大改动悄悄进入。

** 40. 用一个 Property Read 证明整个架构，而不是先实现所有功能


这是目前项目推进方式最有代表性的一篇。

Property Read 作为第一条纵向 architecture slice，要穿过：

#+BEGIN_SRC yaml
Planner
 -> Binding
 -> Servient
 -> Handler
 -> Response
 -> Generation
 -> Cleanup
#+END_SRC

它的价值是尽早证明所有模块边界能够真正组合，而不是分别写出一堆“看起来合理”的 trait。当前仓库也把 PROPERTY-READ-ARCHITECTURE 定义为首个可执行组合证明。
